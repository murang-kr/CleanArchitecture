# 증거 기반 분석

핵심: **관측하지 않은 것을 주장하지 않는다.** 아래 검사는 해당 주장에 필요한 항목만 적용한다. 미사용 여부를 묻지 않는 국소 코드 설명에 전체 에셋·간접 호출 조사를 추가하지 않는다. 이미 읽은 코드와 이번 작업의 증거가 바뀌지 않았다면 재사용하고 관련 변경·불일치가 있을 때 다시 관측한다.

## 관측 증거 계층

관측한 상태의 종류를 E1–E4로 기록한다. 이는 `plan-gate`의 완료 검증 티어 V0–V2와 다른 축이다. V0–V2는 작업 위험에 따라 필요한 검증의 양을 정하고, E1–E4는 각 증거가 어디까지 관측했는지와 주장 가능한 상한을 정한다. 따라서 같은 작업에 둘을 함께 쓴다.

| 계층 | 직접 관측한 상태 | Unity 예시 | 주장 가능한 범위 |
| --- | --- | --- | --- |
| E1 | 정적·저장 직렬화 상태 | `unity vcs diff`의 Scene·Prefab Git 전후 상태 | 저장된 오브젝트·컴포넌트·필드 변화 |
| E2 | Editor가 로드한 상태 | uloop 동적 코드, `SerializedObject`, Hierarchy 조회 | 현재 Editor 메모리의 구조·값 |
| E3 | Editor 실행 결과 | 컴파일, Edit/Play Mode 테스트, Console | 테스트가 실행한 Editor 동작 |
| E4 | 대상 런타임 결과 | Development Player·기기 스모크 테스트 | 해당 빌드·환경의 런타임 동작 |

증거가 관측한 계층을 넘어서는 결론을 내리지 않는다. E1에서 필드가 바뀐 사실만으로 런타임 효과를 단정할 수 없고, E2에서 값이 보인 사실만으로 Player 동작을 단정할 수 없다.

## 규칙

1. **추측 금지** — 변수명·클래스명·파일 경로·주석·**커밋 메시지·PR 제목·이슈 설명**만 보고 동작을 단정하지 않는다. 사람이 쓴 산문은 코드 근거가 아니며, 실제 구현과 어긋나 있는 경우가 흔하다. 모든 핵심 주장은 실제로 읽은 코드 본문을 근거로 한다.
2. **본문 관측 의무** — 분석 대상 코드는 본문을 직접 읽는다. 검색 결과 스니펫이나 파일명 매칭만으로 결론 내리지 않는다.
3. **호출부 추적** — 대상 심볼(클래스·메서드·필드)의 참조·호출부를 실제 검색으로 확인하고, 진입점→대상까지의 호출 체인을 추적해 "실제로 실행되는 경로"인지 판별한다. LSP 기반 참조 추적 도구가 세션에 로드돼 있으면 텍스트 검색보다 우선한다 — 동명 심볼·오버로드·선언/호출 구분을 기계적으로 해결한다. 텍스트 검색만 가능하면 그 한계(동명 혼입 가능성)를 인지하고 교차 확인한다.
4. **죽은 코드 판정 기준 (코드 → 에셋 방향)** — 코드 검색에서 호출부가 없어도 즉시 "죽은 코드"로 단정하지 않는다. 해당 스택의 코드 외 참조 메커니즘을 확인한다:
   - 데이터 참조 (Unity 스택 예): 씬(.unity)·프리팹(.prefab)·ScriptableObject(.asset)의 참조. SerializeReference 기반 참조는 guid가 아니라 `class: 타입명`으로 검색해야 잡힌다.
   - 간접 호출 (Unity 스택 예): 리플렉션, UnityEvent, Animation Event, Addressable, DI 컨테이너, 문자열 기반 Invoke/SendMessage. 다른 스택이면 그에 상응하는 메커니즘(DI 설정, 라우팅 테이블, 직렬화 설정 등)을 확인한다.
   - 위를 확인할 수 없었으면 "죽은 코드 후보 (에셋 참조 미확인)"처럼 확인한 범위를 명시한다.
5. **죽은 데이터 판정 기준 (에셋 → 코드 방향)** — 에셋·설정 파일의 필드값을 근거로 동작을 설명할 때는, 그 필드를 **읽는 코드(read site)**를 검색해 확인한다. **필드의 존재는 사용의 근거가 아니다.** 데이터 주도 설계에서는 값이 채워져 있어도 아무도 읽지 않는 필드가 흔하다.
   - 읽는 곳을 찾지 못하면 "미사용 후보"로 보고한다.
   - 같은 이름의 필드가 여러 객체에 존재할 수 있다. 읽는 쪽이 참조하는 객체가 **내가 본 그 에셋에서 온 것인지**까지 확인한다. (예: 런타임 값이 별도 객체에 복사되어, 에셋의 동명 필드는 읽히지 않는 경우)
   - 읽는 코드가 조건 분기 안에 있으면, **현재 데이터가 실제로 그 분기에 진입하는지**(모드·플래그 필드 값)까지 확인해야 "사용됨"으로 판정한다. 분기에 안 들어가는 필드는 값이 채워져 있어도 죽은 데이터다.
6. **근거 표기** — 핵심 주장마다 `파일경로:줄번호` 근거를 표기한다.
7. **확인/추정 구분** — 직접 관측으로 확인한 사실과 추정을 구분해 보고한다. 추정은 "추정 (미확인)"으로 명시한다.
8. **한계 명시** — 접근 불가하거나 확인하지 못한 부분은 분석 결과에 그 한계를 명시한다.
9. **부연과 과거 기록** — 참고 설명에도 같은 증거 기준을 적용한다. 과거 기록의 경로·동작은 현재 코드로 재검증하고, 확인하지 못한 내용은 미확인으로 구분한다.
10. **직렬화 값 디코딩 검증** — YAML/프리팹/에셋의 enum 정수·비트마스크·인덱스 값은 그 자체로는 관측이 아니다. 대응하는 선언부(enum 정의·레이어 테이블 등)를 같은 분석 안에서 직접 읽어 매핑한 뒤에만 라벨로 서술하고, 매핑 근거(선언 파일:줄)를 표기한다. 에디터/런타임 실측 도구로 교차 검증이 가능하면 그쪽을 우선한다(예: Unity 스택이면 인스펙터·uloop 동적 코드로 라벨 출력).
   - **Unity `.asset`(ScriptableObject)의 필드·값은 YAML을 직독하지 않는다** — YAML은 그 파일이 마지막 저장된 시점의 스냅샷이라 필드명·필드 목록이 현재 클래스와 어긋날 수 있다(같은 폴더 안에서도 파일마다 다름). `unity-so-readout` 스킬로 덤프해 읽는다. Unity가 꺼져 있어 부득이 YAML을 읽었으면 결론에 그 한계를 명시한다.
11. **외부 패키지 API 검증** — 서드파티 패키지·라이브러리 API의 시그니처·동작을 근거로 삼을 때는 사전지식·웹 문서가 아니라 설치본을 관측한다: 락파일에서 실제 설치 버전을 확인하고, 설치된 패키지 소스의 선언부를 직접 읽는다 (Unity 스택 예: `Packages/packages-lock.json` + `Library/PackageCache/<패키지>@<버전>/`. 다른 스택이면 node_modules·site-packages 등 상응 위치). 설치본을 관측할 수 없으면 해당 버전이 명시된 공식 문서를 차선으로 쓰고 그 한계를 명시한다.
12. **Unity Scene·Prefab 변경 증거** — `.unity`·`.prefab`의 Git 저장 상태나 전후 변화를 조사할 때는 raw YAML diff보다 `unity-vcs-evidence` 스킬의 읽기 전용 JSON을 E1 기본 증거로 사용한다. 기계 판정은 Unity 원본 `changedFields`의 raw 직렬화 필드명(공용 출력 `normalizedChanges[].fields`)으로 하고 `fieldLabels`·`summary`는 제공될 때 표시용으로만 쓴다. 현재 Editor 상태는 uloop 기반 E2를, 동작 주장은 read site와 E3/E4를 추가한다. CLI 실패를 조용히 YAML 직독으로 대체하지 않는다.
