# 구현 게이트

구현을 시작하기 전에 아래 3단계를 순서대로 완료한다. **승인 전에는 파일을 수정하지 않는다.**

## 1. 구현 계획 수립

- 변경할 파일 목록과 파일별 변경 내용 요약
- 변경 범위: 영향받는 시스템·기능 (직접 수정하지 않지만 동작이 바뀌는 곳 포함)
- 검증 계획: 완료 검증 티어 V0–V2를 선언하고, 어떤 명령으로 어떤 증거를 낼지 명시한다. 작업 중 티어 하향 금지. V0–V2는 작업 위험에 따른 완료 검증량이며, `evidence-analysis`의 관측 증거 계층 E1–E4와 다른 축이므로 필요한 계층을 함께 명시한다.
  - **V0** — 에셋·수치·텍스트·설정만: 컴파일 클린
  - **V1** — 기존 로직 수정·버그픽스: + 관련 기존 테스트 통과, 버그픽스는 RED→GREEN(수정 전 재현 증거 → 수정 후 통과 증거)
  - **V2** — 신규 핵심 로직·시스템: + 판정 로직에 대한 자동화 기능 테스트 신설(프로젝트의 테스트 프레임워크 사용). 테스트 수단이 없으면 테스트 작성까지가 작업 범위다(계획에 명시)
- Scene·Prefab 변경 계획은 `unity-vcs-evidence`가 대조할 예상 변화 계약을 가능한 범위에서 기록한다: asset 경로, owner GameObject, component, raw 직렬화 field, change kind. 현재 Editor 상태나 런타임 효과까지 주장한다면 E2–E4 추가 관측도 계획한다.
- 사람 검수 항목 분리: 지각·감성 오라클이 필요한 항목(UX·룩앤필·체감 품질 등)은 AI 검증 대상에서 제외하고 확인 포인트 목록으로 정리한다
- 인터뷰를 거친 작업이면: 계획이 Seed 요약(확정 요구사항)을 모두 커버하는지 확인하고, 벗어나거나 추가되는 항목은 사유를 명시한다
- 설계 결정이 포함된 구현이면(새 UX·컨셉·구조 등 선택지가 존재하면): 계획 확정 전에 접근법 3~5개를 서로 다른 축에서 제시한다 — 각각 기존 구조 준수 여부·실패 모드·변경 비용을 명시하고, 추천 1개를 표시하되 선택은 사용자가 한다
- 계획 작성 중 드러난 미해소 지점은 임의 추정으로 조용히 메우지 않는다: 합리적 기본값이 있으면 채택했음을 계획에 명시하고, 없으면 해당 위치에 `[미해소: 질문]` 마커를 남긴다 — 최대 3개, 초과분은 영향 큰 순으로 추리며 우선순위는 범위 > 데이터·안전 > UX > 기술 디테일. 컨펌 요청 시 마커를 질문 목록으로 모아 승인과 함께 일괄 해소한다. 대화형 세션에서는 마커 목록을 선택지 형태의 질문으로 제시해 해소하는 것을 동등 이행으로 인정한다(대화형 질문 UI가 있으면 그것을 사용) — 마커 표기는 영속화된 계획 문서 등 비대화 산출물에서 유지한다. (착수 전에 물어야 하는 근본 모호성 — 대상·목표·완료 기준 — 은 마커가 아니라 게이트의 사전 질문 대상이다)

## 2. 구조 점검 — 위반이 있으면 계획을 수정한 뒤 진행

- **YAGNI**: 요청되지 않은 기능·설정·확장성이 계획에 들어있지 않은가
- **KISS**: 같은 요구를 만족하는 더 단순한 설계는 없는가
- **DRY**: 기존 코드·유틸을 검색해 재사용했는가, 중복 구현이 없는가
- **SRP**: 새로 만들거나 수정하는 단위(클래스·함수)가 한 가지 책임만 갖는가
- **소유권 조사** — DRY·SRP는 예/아니오 자기 채점으로 통과 처리하지 않는다. 계획이 신규 파일·클래스·코드 경로를 신설하면, 신설 단위마다 계획에 기재한다:
  - 같은 관심사(감지·판정·매핑·UI 배선 등 같은 축)를 이미 소유한 기존 시스템 — 실측한 파일 경로·심볼 인용. "없음"이면 무엇을 어떻게 검색했는지 근거를 남긴다.
  - 기존 시스템의 확장이 아니라 병렬 신설인 경우 — 확장이 불가능한 사유. 사유를 실측으로 뒷받침하지 못하면 신설하지 않고 기존 시스템 확장으로 계획을 수정한다.
  - 확장/신설 판별 기준: 기존 소유자(핸들러·리스트·컴포넌트)를 그대로 두고 그 안에 필드·분기를 늘리면 "확장"이다. 소유권·책임을 새 단위로 옮기면 어떤 명분(중복 수렴·DRY·재사용)을 붙여도 "신설·이관"이며 반드시 사전 컨펌 대상이다 — 중복 수렴 여부는 사용자가 결정한다.
- **예측 가능성**: 새 이름(클래스·필드·씬 오브젝트)만 보고 처음 보는 사람이 내용물을 예측할 수 있는가. 변경으로 기존 이름의 의미가 넓어지면 개명을 같은 계획에 포함한다. 구조·네이밍 컨벤션 결정은 자율 확정하지 않고 컨펌 대상에 올린다.

## 3. 최종 컨펌

- **V2 계획은 컨펌 요청 전에 `plan-critic` 검증 패스를 거친다**: 서브에이전트를 띄울 수 있으면 `.agents/skills/plan-critic/SKILL.md`를 프롬프트로 주어 위임하고, 없으면 그 절차를 계획 작성과 분리된 별도 패스로 직접 수행한다(적대적 시각 유지). 블로커(최대 3개)가 나오면 계획을 수정한 뒤, 리뷰 결과(OKAY 또는 해소한 블로커)를 컨펌 요청에 첨부한다. 리뷰는 사용자 컨펌을 대체하지 않는다. 스킬 파일이 없으면 생략하고 그 사실을 밝힌다.
- 계획과 변경 범위를 사용자에게 설명하고 **명시적 승인을 받은 뒤에만** 구현을 시작한다.
- 승인된 계획을 파일로 유지해야 하는 작업은 프로젝트 `AGENTS.md`의 개발 기록 정책과 `Docs/Development-Record-Format.md`를 따라 `Docs/development-record/DEV-<YYYY>-<NNN>-<슬러그>.md` 하나에 저장한다.
  - 같은 사용자 목표의 기록이 있으면 새 파일을 만들지 않고 기존 기록을 갱신한다. 새 목표라면 `Docs/development-record/Index.md`에서 다음 ID를 확인해 기록을 만들고 인덱스에 한 줄 포인터를 추가한다.
  - 승인 직후 계획 원문, 변경 예정 파일, 영향 범위, Non-goals, 구조·소유권 점검, 증거 티어와 검증 명령, 사람 검수 항목, `plan-critic` 결과를 기록하고 상태를 `approved` 또는 구현 착수 시 `in_progress`로 둔다.
  - 구현 중 실행 기록을 같은 문서에 누적하고, 완료 시 변경 내용·검증 증거·최종 결과를 추가한 뒤 상태를 `completed`로 갱신한다. 중단되면 상태와 재개 조건을 기록한다.
  - `.codex/plans/`를 포함해 별도 계획 문서를 만들지 않는다. 이후 세션의 재개·완료 검증은 요약 기억이 아니라 이 개발 기록 정본과 대조한다.
- 이번 대화에서 이미 승인된 계획의 연속 작업이면 게이트를 반복하지 않는다.
- 분석 턴에서 제시한 방안을 사용자가 선택해 착수하는 경우: 1·2절 재작성은 생략하되, 착수 선언에 **완료 검증 티어·필요 관측 계층과 검증 계획 한 줄**을 명시한 뒤 진행한다. V2면 plan-critic 리뷰는 생략하지 않는다.
- **구현 중 정지선**: 승인 이후 구현 중에 기존 구조를 따르는 코드와 충돌하거나, 계획에 없던 신규 단위·소유권 이동·우회 경로가 필요해지면 이는 계획 결함 신호다. 신설 코드가 이기도록 즉석 우회로를 만들지 말고, 작업을 멈추고 충돌 내용을 보고한 뒤 계획 수정 재컨펌을 받는다.
- 구현 완료 후에는 계획 대비 실제 변경 내역을 보고하고, 검증 결과는 **4. 완료 증거 계약**에 따라 보고한다.

## 4. 완료 증거 계약

- 완료 선언에는 선언한 티어의 **신선한 증거 인용**이 필수다: 하네스 바인딩(`.codex/harness-bindings.json`, 없으면 `.claude/harness-bindings.json`) 또는 프로젝트 문서에 정의된 컴파일·테스트 명령의 실제 출력. "될 것이다", "로직상 맞다"는 증거가 아니다. 증거를 낼 수 없으면 "완료"가 아니라 **"미검증"으로 명시해 보고**한다.
- 버그픽스는 RED→GREEN: 수정 전에 실패/재현 증거를 먼저 확보하고, 수정 후 같은 방법으로 통과 증거를 캡처한다.
- 금지: 통과를 위한 스코프 축소, 실패 테스트 삭제·비활성화·완화, 판정 로직을 우회하는 테스트 전용 분기. 테스트 모드는 구동·관측만 다르게 하고(스폰 강제·시간 가속·시드 고정·상태 덤프) **판정 로직은 프로덕션 경로를 그대로 탄다**.
- 완료 보고 양식: ① AI 검증 완료 — 완료 검증 티어(V0–V2)·사용한 관측 계층(E1–E4)·증거 인용 ② 사람 검수 필요 — 지각 오라클 확인 포인트 목록
  - 적용 범위: ①② 양식은 티어 선언을 동반한 **계획 단위 작업**의 완료 보고에 적용한다. 계획 단위가 아닌 단발 소수정(한 파일·한 원인)의 완료 보고는 신선한 증거 인용만 필수로 하고 양식은 생략할 수 있다 — 증거 없는 완료 선언 금지는 규모와 무관하게 유지된다.
- **요구사항이 4개 이상인 작업**은 완료 보고에 요구사항별 → 증거 매핑표를 포함한다 — 누락 항목이 "완료" 뒤에 숨는 것을 막는다. 소형 작업은 기본 양식만 쓴다.
