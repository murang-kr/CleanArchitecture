# 변경 계획과 검증

작업 분류·승인 경계는 프로젝트 `AGENTS.md`가 정본이다. 명확한 요청 범위의 통상적 수정은 계획을 간단히 밝히고 진행한다. 계획 검토만 요청받았다면 구현하지 않는다. 이미 승인된 계획의 연속 작업은 계획·승인을 반복하지 않는다.

## 계획과 구조 점검

- 변경 파일·결과·영향 범위와 검증 명령을 작업 크기에 맞게 정한다. 한 파일의 사소한 수정은 한두 문장으로 충분하다.
- 기존 관심사의 소유자를 실제 코드에서 찾아 확장한다. 새 단위가 필요하면 기존 소유자와 신설 이유를 명시한다. 같은 책임을 병렬로 신설하거나 요청되지 않은 추상화·설정을 추가하지 않는다.
- 파일명·함수 분리·기존 구조를 따르는 내부 선택은 자율 판단한다. 공개 계약·계층 책임·타입 소유권을 바꾸는 선택은 사용자에게 영향을 설명하고 확인한다. 명명만으로 실질적인 소유권 변경을 감추지 않는다.
- 선택지가 결과를 크게 바꿀 때만 실질적인 대안과 권고를 제시한다. 대안 개수를 채우기 위해 선택지를 만들지 않는다.
- 합리적 기본값은 필요할 때 가정으로 밝히고 진행한다. 범위·계약·데이터에 중요한 미확정 요구는 확인하고, 답변과 독립적인 조사는 계속한다.
- 아키텍처 문서 동시 갱신 여부는 AGENTS.md의 구조 변경 기준으로 판단한다.

## 검증량

V0–V2는 위험에 따른 검증량이다. Unity의 E1–E4 관측 계층과 혼동하지 않는다.

| 티어 | 적용 | 필요한 검증 |
|---|---|---|
| V0 | 문서·수치·설정 등 실행 로직 변경 없음 | 변경 대상의 형식·참조·정합성 검사. Unity 에셋·설정에 영향이 있으면 관련 로드·컴파일 또는 동작 관측 추가 |
| V1 | 기존 로직 수정·버그 수정 | 관련 실행 환경의 구문·컴파일 검사와 관련 테스트. 버그는 수정 전 재현 → 수정 후 같은 검사 통과 |
| V2 | 신규 핵심 로직·시스템 | V1 + 핵심 판정의 자동화 기능 테스트. 테스트 수단이 없으면 테스트 작성도 범위에 포함 |

- 검증 명령은 `.codex/harness-bindings.json`(없으면 `.claude/harness-bindings.json`)이나 프로젝트 문서에서 **변경 대상에 맞는 항목**을 선택한다. Node 훅 변경은 Node 검사·테스트를 사용하며 Unity 컴파일을 일괄 추가하지 않는다.
- 통과 후에는 새 변경·실패·미해결 우려가 있을 때만 검증을 넓히거나 반복한다. 단순 문구 변경을 그대로 대조하는 테스트는 만들지 않는다.
- Scene·Prefab 변경은 `unity-vcs-evidence`가 있을 때 예상 `asset / owner / component / raw field / change kind`를 계획에 적고 E1 결과와 대조한다. 현재 Editor·런타임 효과 주장은 필요한 E2–E4를 추가한다. 스킬이 없는 프로젝트는 사용 가능한 관측 방법과 한계를 명시한다.
- V2 계획은 실행 전 `plan-critic`으로 파일·소유권·검증 명령의 실행 가능성을 검토한다. 독립 검토와 사용자 승인은 서로 대체하지 않는다.

## 실행과 기록

- 기록 대상 작업은 `Docs/Development-Record-Format.md`에 따라 `Docs/development-record/DEV-<YYYY>-<NNN>-<슬러그>.md` 하나에 계획·실행·증거·결과를 보관한다. 같은 목표는 기존 기록을 갱신하며 별도 계획 파일을 만들지 않는다.
- 별도 승인이 필요한 작업은 승인 직후 기록한다. 그 외에는 명확한 요청을 근거로 착수하면서 `in_progress`로 기록하고 승인 필요 여부를 구분한다. 새 기록의 ID는 Index.md에서 확인하며 한 줄 포인터를 추가한다.
- 예상 밖 코드가 나와도 승인 범위·계약 안의 해결은 계속한다. 범위 확대·중요 계약 변경·소유권 이동이 필요하면 해당 변경을 멈추고 영향과 수정 계획을 확인한다. 독립적으로 완료 가능한 작업까지 중단하지 않는다.

## 완료 증거

- 완료는 실제 출력·산출물로 뒷받침한다. 실행 명령·대상·결과·검증 시점 이후 관련 변경 여부를 확인한다. 코드와 환경이 일치하는 이번 작업의 증거는 재사용할 수 있다. 과거 요약이나 완료 선언만으로 통과 처리하지 않는다.
- 증거가 없거나 일부만 관측했으면 해당 항목을 미검증으로 보고한다. 실패 테스트 삭제·완화·비활성화, 테스트 전용 판정 우회, 통과를 위한 범위 축소는 금지한다.
- 최종 보고는 결과·관련 검증·남은 한계를 중심으로 쓴다. 많은 요구사항의 대응표는 DEV 기록에 두고 대화에서는 핵심만 보고한다. 사람의 지각 판단이 필요한 항목은 해당할 때만 별도로 남긴다.
